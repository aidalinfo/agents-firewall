# L4 — Plugin Hermes (`integrations/hermes/`) — plan détaillé

> Pour les agents : exécution inline, TDD strict (tests de contournement d'abord pour l'étage intention).

**Goal :** fournir le paquet Python `afw-hermes` (stdlib uniquement à l'exécution) qui, chargé par Hermes
(plugin `register(ctx)` ou hook shell `pre_tool_call`), envoie les `ToolCallEvent` à la console pour la
corrélation (EF-34, EF-61, ADR 0007) et applique les classes d'actions de l'egress-guard avec leur « gate »
(EF-62, conception §9 et §15).

**Architecture :** `config` (env + fichier) → `events` (dataclass + résumé masqué) → `sender` (file bornée,
thread d'envoi groupé, backoff, spool disque borné) ; `intent` (politique distante mise en cache, repli
disque puis politique intégrée, évaluation déterministe) ; `plugin` (hooks en processus) ; `hook` (mode CLI
stdin/stdout, compatible hooks shell Hermes et egress-guard) ; `flush` (vidage détaché du spool et
rafraîchissement de la politique pour le mode CLI). Démo : faux agent Hermes piloté en HTTP.

**Tech Stack :** Python ≥ 3.11 (urllib, json, threading, queue, ssl), pytest (dev).

## Mécanisme Hermes retenu (vérifié dans la documentation publique Hermes Agent)
- Plugin : dossier `~/.hermes/plugins/<nom>/` avec `plugin.yaml` + `__init__.py` exposant `register(ctx)`,
  ou paquet pip avec point d'entrée `hermes_agent.plugins` ; activation par `plugins.enabled`.
- `ctx.register_hook("pre_tool_call", cb)` ; `cb(tool_name, args, task_id, **kwargs)` (kwargs : `session_id`,
  `tool_call_id`…) ; blocage = retour `{"action": "block", "message": "..."}`.
- `post_tool_call` : `cb(tool_name, args, result, task_id, duration_ms, **kwargs)` (kwargs : `status`…).
- Hook shell (`hooks:` de `config.yaml`) : JSON sur stdin (`hook_event_name`, `tool_name`, `tool_input`,
  `session_id`, `extra`) ; blocage par `{"action":"block","message":..}` / `{"decision":"block","reason":..}`
  ou code de sortie 2.

## Tâches
1. Squelette `pyproject.toml` (paquet `afw-hermes`, point d'entrée `hermes_agent.plugins`), `conftest.py`.
2. `events` : tests sérialisation exacte (clés, ordre, RFC3339 `Z`, `null`), masquage (Bearer, clés
   `password/token/secret/api_key`, `sk-…`, `ghp_…`, `AKIA…`, JWT, URL `user:pass@`, clé privée PEM),
   troncature 500 car. → implémentation.
3. `config` : tests env > fichier > défauts, YAML plat minimal, JSON → implémentation.
4. `intent` : tests de contournement d'abord (variantes `rm -r -f`, `rm -fr`, `rm --recursive --force`,
   majuscules, arguments imbriqués, nom d'outil en casse différente, `kubectl -n x delete`, `docker
   container rm`, `terraform destroy -auto-approve`, etc.), chaque classe détectée, plus stricte des décisions,
   message de gate, politique distante appliquée, politique invalide rejetée (dernière valide conservée), repli
   cache disque puis politique intégrée → implémentation.
5. `sender` : tests non bloquant (serveur qui dort, `enqueue` < 50 ms), lot `{"events":[...]}` avec en-tête
   `Authorization: Bearer`, réessai après panne, spool disque borné puis vidage → implémentation.
6. `plugin` : tests `register(ctx)` enregistre deux hooks, `pre_tool_call` bloque une classe gate et laisse
   passer le reste, début/fin envoyés avec le même `id`, `conversation_id` depuis `session_id`/`task_id`.
7. `hook` + `flush` : tests CLI (stdin/stdout, code 2 sur blocage, format egress-guard `tool`/`args`,
   corrélation pré/post via fichiers en attente) → implémentation.
8. Démo : `demo/fake_hermes.py` + `demo/Dockerfile.demo` ; test du serveur de commande.
9. `README.md`, ADR 0015, vérification Docker, commit, PR vers `dev`.

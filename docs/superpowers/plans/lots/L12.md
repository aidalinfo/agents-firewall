# L12 — Déploiement et environnement de démo — plan détaillé

> Pour les agents : exécution inline, TDD (les tests de `deploy/tests/` sont écrits avant les fichiers qu'ils
> vérifient ; le test d'isolement du conteneur `afw-net` est un test de contournement).

**Goal :** livrer les images (API, netinit, CLI), le `docker compose` de production (console + API + Postgres,
ClickHouse en profil), le compose de la passerelle, le chart Helm et l'environnement de recette `demo/`
complet et hermétique (aucun service Internet), prêts à fonctionner dès que les binaires des autres lots
existent (ENF-06, cahier §9, recette §8).

**Architecture :** tout se construit et se vérifie dans Docker. La démo assemble quatre réseaux : `control`
(console, API, Postgres, passerelle ; seul réseau publié sur l'hôte, en 127.0.0.1), `afw-internal`
(internal, 10.77.0.0/24 : passerelle + conteneurs `afw-net-<agent>`), `lan` (internal, 10.78.0.0/24 :
`internal-db`, réseau interne simulé) et `wan` (internal, 198.18.0.0/24 : « Internet » simulé — CoreDNS de
démo, faux fournisseur LLM, cible d'exfiltration, API autorisée, faux S3). 198.18.0.0/15 (plage de test,
RFC 2544) n'est pas dans les réseaux internes par défaut de la politique : les fausses destinations
publiques sont donc traitées comme Internet. Une CA de démo (openssl dans l'image `afw-demo-tools`) signe le
certificat des faux services ; la passerelle lui fait confiance en amont.
Les appels API sont regroupés dans `demo/lib.sh` (un seul endroit à corriger quand l'OpenAPI sera fusionné).

**Tech Stack :** Docker / Compose v2, Helm 3 (alpine/helm), CoreDNS 1.11 (Apache 2.0), Python 3.12 stdlib
(faux services), bash + curl + jq, shellcheck.
